# Agent Note: SDK cohort 0.2.2-rc.2

Status: implemented

## Problem

The community-plugin index and its inert compatibility row tracked the 0.2.2-rc.1 cohort while the supported host moved to the published 0.2.2-rc.2 release. The cohort, the release-age ledger and the declared host floor need to advance together, without altering the community catalog or the inert row's semantics.

This repository consumes a deliberately small slice of the SDK: `src/index.ts` imports only the Cordis `Context` type, and the client-bundle preset in `shared/tsdown.client.ts` names SDK packages as string literals. The rc.2 removals (internal subpath exports such as `@deepseek-ai/dsh-subagent/internal`, the `startActivation` field nesting and the `drainChildren`/`drainDescendants` shapes) therefore have no call site here.

## Decision

SDK development dependencies move from `^0.2.2-rc.1` to `^0.2.2-rc.2`; Cordis stays at `^4.1.0`. The host engine floor `dsh.engines.dsh` and the `@deepseek-ai/dsh` peer move from `>=0.2.2-rc.1` to `>=0.2.2-rc.2`, so a host below rc.2 no longer satisfies the declaration.

The lockfile is regenerated in place, and the release-age exclusion ledger moves as a straight version bump: the 323 rc.1 entries become rc.2 entries, and pnpm appends the 14 packages that the rc.2 cohort introduces (`dsh-agent-team`, `dsh-client-ui-account-notifications`, `dsh-client-ui-agent-team`, `dsh-computer-use`, `dsh-cua`, `dsh-cua-bundle`, `dsh-error`, `dsh-experimental-cua-macos`, `dsh-mcp-manager`, `dsh-office-kit`, `dsh-terminal-panel`, `dsh-tool-agent-team`, `dsh-tool-office`, `dsh-util-ripgrep`), for 337 entries in total.

The bilingual README badges carry the floor label, so both sides move from `>=0.2.2-rc.1` to `>=0.2.2-rc.2` and the `README.i18n.yaml` pairing hashes are re-recorded. The inert Cordis row, the community catalog and the eleven-module browser platform table remain unchanged.

## Alternatives considered

**Stay on 0.2.2-rc.1 declarations under a 0.2.2-rc.2 host.** Rejected: the declared floor would understate the host the package is actually built and tested against, and the repository would keep resolving a cohort that no longer matches the family it ships with.

**Rewrite catalog entries that name 0.2.2-rc.1.** Rejected: those strings are third-party store copy describing each plugin's own compatibility (its `engines.dsh` range and the host it was verified on), so they are upstream facts rather than this repository's cohort. Catalog curation stays independent of SDK cohort alignment.

**Publish a new npm version as part of the cohort move.** Rejected: no release was requested for this change, so `version` stays at 0.4.17 and the family coordinates the release separately.

## Consequences

No source adaptation was required: rc.2 broke no call site, so the only code-adjacent edits are the version declarations.

`pnpm install --frozen-lockfile --ignore-scripts` passes supply-chain policy verification (839 entries). `pnpm community:check` (124 entries), the 10 index script tests, `pnpm typecheck`, the 3 Vitest tests and `pnpm build` all pass against the installed rc.2 packages. No package is published to npm; dsh-web links the updated working tree locally through its satellite profile workflow.
